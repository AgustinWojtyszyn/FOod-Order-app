Riesgos residuales
==================

1. Migraciones historicas
-------------------------

Hay migraciones anteriores que contienen validacion vieja 9-22.
Esto es normal porque no se editan migraciones historicas.
La migracion nueva redefine create_order_idempotent y debe ser la ultima aplicada para que gane la version nueva.


2. Dependencia de location textual
----------------------------------

get_order_schedule_context usa p_location textual normalizado.
Esto es compatible con el flujo actual, pero si en el futuro se agregan sedes con nombres parecidos, convendria migrar a location_id o slug canonico.


3. Fallback frontend
--------------------

Si la llamada al RPC falla, useOrderSchedule cae a DEFAULT_SCHEDULE_CONTEXT cerrado/default.
Esto evita permitir pedidos sin validacion horaria, pero puede bloquear temporalmente si el backend esta caido.


4. Cambio de empresa
--------------------

change_active_company_for_today ahora valida horario de la sede destino.
Eso preserva la semantica de "dentro del horario de pedidos" por sede, pero puede cambiar el comportamiento de usuarios que antes podian cambiar empresa hasta 22:00 aunque la nueva sede ahora sea standard y cierre 14:00.


5. Servicios admin parciales
----------------------------

supabase status mostro algunos servicios detenidos.
La DB local estaba disponible y se valido SQL alli.
No se probaron Edge Functions end-to-end porque edge_runtime estaba detenido.
